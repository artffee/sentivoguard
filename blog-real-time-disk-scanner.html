How we built a real-time disk scanner in Node.js with zero external dependencies

SentivoGuard scans 16,000 files in 7.6 seconds, streams findings to the UI as they're discovered, and runs on Windows, macOS, and Linux without a single npm install. Here's the architecture.

The constraint shaped the design

Spec said: zero external dependencies in the scanner core. No chokidar, no fast-glob, no native bindings. Just Node's standard library.

At first this felt like a handicap. By the end it was a feature. Every external dep is a supply-chain attack surface — and we're literally building a supply-chain scanner. Eating our own dogfood meant the scanner couldn't depend on the kind of code it was designed to flag.

That ruled out streaming libraries (through2, highland), watcher libraries (chokidar), and even regex generators. Everything had to come from node:fs, node:path, node:crypto, node:http, and friends.

The async-generator backbone

The scanner is an async generator. It yields four event types: start (with the resolved roots), progress (every 100 files), finding (per detection), and complete (verdict + final stats). The HTTP layer just consumes the generator and forwards each event over the wire. 

// server/scanner-disk.js
async function* scanDisk(opts = {}) {
  const start = Date.now();
  const roots = opts.quick ? quickScanPaths() : [opts.target];

  yield { type: "start", roots, ts: start };

  for (const root of roots) {
    const queue = [[root, 0]];
    while (queue.length && !opts.aborted) {
      const [dir, depth] = queue.shift();
      const entries = await fsp.readdir(dir, { withFileTypes: true });

      for (const e of entries) {
        if (e.isDirectory()) queue.push([path.join(dir, e.name), depth + 1]);
        else if (e.isFile()) {
          const hits = inspect(path.join(dir, e.name));
          for (const f of hits) yield { type: "finding", ...f };
        }
      }
      if (filesScanned % 100 === 0) {
        yield { type: "progress", filesScanned, currentDir: dir };
        await new Promise(r => setImmediate(r)); // yield to event loop
      }
    }
  }

  yield { type: "complete", verdict, exitCode, stats };
}

The setImmediate yield every 100 files matters more than it looks. Without it, a long scan blocks the event loop and the same Node process can't answer other HTTP requests. The 100-file cadence keeps the server responsive without flooding the loop with microtasks.

NDJSON over chunked HTTP

We needed to stream findings to the browser as they happened — not wait for the full scan to finish. Three options:

  • Server-Sent Events. Standard, has EventSource API. But limited to GET, can't carry a JSON body cleanly, and reconnect logic adds complexity.
  • WebSockets. Bidirectional, but overkill for one-way streaming. Adds a handshake and a separate connection lifecycle.
  • NDJSON over chunked HTTP. Plain POST. Each chunk is one JSON object on its own line. Browser reads it via fetch().body.getReader().

We picked NDJSON. It's the simplest thing that works, plays nicely with AbortController for cancellation, and lets us send a request body alongside the streaming response. The parsing on both ends is a one-liner. 

// .server.js — the endpoint
if (pathname === "/api/scan/disk") {
  res.writeHead(200, {
    "content-type": "application/x-ndjson",
    "x-accel-buffering": "no"          // disable proxy buffering
  });

  req.on("close", () => { opts.aborted = true; });   // client gone? stop scanning

  for await (const ev of scanDisk(opts)) {
    if (opts.aborted) break;
    if (!res.write(JSON.stringify(ev) + "\n")) {
      await new Promise(r => res.once("drain", r)); // honor backpressure
    }
  }
  res.end();
}
// js/backend.js — the client
const r = await fetch("/api/scan/disk", { method: "POST", body, signal: ctrl.signal });
const reader = r.body.getReader();
const dec = new TextDecoder();
let buf = "";

while (true) {
  const { value, done } = await reader.read();
  if (done) break;
  buf += dec.decode(value, { stream: true });
  let nl;
  while ((nl = buf.indexOf("\n")) >= 0) {
    onEvent(JSON.parse(buf.slice(0, nl)));   // progress / finding / complete
    buf = buf.slice(nl + 1);
  }
}

Two tricks worth calling out. First, the x-accel-buffering: no header tells reverse proxies (nginx, Cloudflare) not to buffer the response — without it, our chunks would pile up on the proxy and only flush when the response ended, defeating the whole point. Second, we honor backpressure: if res.write returns false we wait for drain before yielding more. Otherwise a slow client makes the server allocate unbounded memory.

The pattern engine

Detection is regex-based, organized into eight categories: credential theft, network exfil, code execution, obfuscation, persistence, cryptomining, ransomware, and Windows-shell droppers. Each pattern has a severity (HIGH, MEDIUM, LOW) and a one-line message. 

const PATTERNS = {
  credential_theft: [
    p(/keytar\.(?:get|find)Password\(/g, HIGH,
      "Reads stored credentials from system keychain"),
    p(/process\.env\.[A-Z_]*(?:KEY|TOKEN|SECRET|PASSWORD)/g, MEDIUM,
      "Reads sensitive environment variable"),
    p(/readFileSync\([^)]*\.ssh[/\\]id_(?:rsa|ed25519)/g, HIGH,
      "Reads private SSH key file"),
    // ...
  ],
  obfuscation: [
    p(/eval\s*\(\s*atob\s*\(/g, HIGH,
      "eval(atob(...)) — decodes and executes base64 payload"),
    p(/['"`][A-Za-z0-9+/=]{300,}['"`]/g, MEDIUM,
      "Very long base64-looking string (possible packed payload)"),
    // ...
  ]
  // ... 6 more categories
};

Two things make this practical. First, the p() helper normalises the regex — every input gets the global flag stripped and re-added so callers don't have to think about it, and we ensure lastIndex resets between files. Second, we cap each rule at three matches per file to avoid pathological cases (a minified file with 4,000 eval calls would otherwise dominate the report).

Filename and location heuristics

Most pattern engines stop at content. Real droppers don't put their suspicious code in a .js we can read — they ship as a compiled .exe in your Downloads folder. So the scanner also runs cheap heuristics on every file based on its name and location:

  • Typo-squatted system processes: svch0st.exe (zero instead of "o"), expIorer.exe (capital I instead of l)
  • Double extensions: invoice.pdf.exe, resume.docx.scr
  • Phishing-themed names: payment_overdue.exe, delivery_tracking.scr
  • Hex-encoded filenames: a1b2c3d4e5f60718.exe (common dropper naming)
  • Risky locations: any executable in %TEMP%, rare extensions like .scr/.pif/.hta in Downloads, executables in AppData/Roaming outside known-vendor folders

The location check is just a list of regexes against the file's path, and it runs in nanoseconds. On the user's machine that ran the live scan, most of the 175 findings came from this layer — not the content patterns. It catches what content scanning can't see.

Real-time monitoring as a thin layer on top

Once the scanner exists, real-time protection is almost free. The watcher daemon runs fs.watch with recursive: true on Downloads, Desktop, the two Temp directories, and AppData/Roaming. When a file event fires, we run the same heuristics we use during a full scan and publish to a pub/sub. 

const w = fs.watch(p, { recursive: true }, (eventType, filename) => {
  if (!filename) return;
  const full = path.join(p, filename);

  // Debounce: same path within 1.5s → one event
  const last = lastSeen.get(full) || 0;
  if (Date.now() - last < 1500) return;
  lastSeen.set(full, Date.now());

  const findings = inspect(full);
  publish({ type: "file_event", path: full, findings });
});

The HTTP side serves the events as Server-Sent Events (yes, SSE here — for fan-out streaming with auto-reconnect, SSE is genuinely the right primitive). The browser's EventSource picks it up, and the renderer pipes events into the activity feed. New file lands in Downloads → activity feed lights up before the user double-clicks.

Cancellation that actually works

Here's the bit nobody talks about: cancellation. Users will click "Cancel" mid-scan. The browser will close the tab. Some scans will take 30 seconds and the user will navigate away in 5.

The whole pipeline cooperates. On the client, we stash an AbortController when starting a scan. Calling abort() tears down the fetch. On the server, the request's "close" event fires the moment the socket drops. The handler flips opts.aborted = true, and on the next yield the async generator notices and bails.

No timers, no polling, no zombie scans. The Node process forgets the scan ever happened within milliseconds of the client closing the tab.

The numbers

On the development machine (a laptop with a not-particularly-fast SSD):

  • Quick Scan paths covered: 8 (Downloads, Desktop, Documents, Temp×2, AppData/Roaming, Startup×2)
  • Files scanned: 16,400
  • Directories walked: 5,266
  • Findings emitted: 175 (70 HIGH, 72 MEDIUM, 33 LOW)
  • Total elapsed: 7.6 seconds
  • Memory peak: under 80 MB
  • External npm dependencies in scanner: 0

Most of the wall-clock time is filesystem I/O, not pattern matching. Once you've fanned out across 16k fs.stat calls, the regex engine is essentially free. We could probably go faster with a worker pool to parallelize file reads — but at 7.6s for the typical user's home directory, the win wouldn't be worth the complexity.

What's next

Three things on deck. First, VirusTotal integration is wired: every finding has a "↗ VT" button that hashes the file and queries 70+ commercial AV engines via the v3 API, with a 24-hour disk cache and free-tier rate limiting. Second, the same scanner core is going to power a VS Code extension that lints every file you save — same patterns, same verdict system, scoped to your project. Third, we're adding YARA-style rule loading so users can write their own detections without touching the codebase.

The full source is on GitHub. The scanner core is in server/scanner-disk.js, the patterns are in server/patterns.js, and the streaming endpoint is in .server.js. The whole pipeline — disk walker, pattern engine, NDJSON streaming, abort handling, real-time watcher, VirusTotal client — comes in under 1,500 lines of Node.
